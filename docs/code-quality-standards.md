# 코드 품질 기준

## 핵심 목표

이 프로젝트는 Android 초보자가 만들기 시작한 코드베이스이며, 이미 좋지 않은 구조와 일관성 없는 코드가 많이 섞여 있다.

따라서 기존 코드를 그대로 반복하는 것이 목표가 아니다. 작업을 이어갈수록 관심사 분리와 레이어링이 명확한 코드베이스로 점진적으로 개선하고, XML 기반 View 시스템에 맞는 MVC 구조와 UDF 흐름을 최대한 지키며, Now in Android, 공식 Android 샘플, Android 권장 아키텍처에 가까운 베스트 프랙티스 수준으로 만들어가는 것이 핵심 목표다.

## 기준

- UI, 상태 처리, 도메인 로직, 데이터 접근 책임을 명확히 분리한다.
- XML 기반 View 시스템을 사용하므로 View, Controller, Model의 책임을 구분하는 MVC 구조를 지킨다.
- 화면은 최대한 단방향 데이터 흐름(UDF)을 따른다. 상태는 한 방향으로 내려가고, 사용자 액션은 이벤트로 올라가며, 상태 변경은 명확한 소유자에서 처리한다.
- Fragment와 Activity는 뷰 바인딩, 생명주기 연결, 내비게이션, 사용자 상호작용 처리에 집중한다.
- ViewModel은 UI 상태를 구성하고 이벤트를 처리하되, 데이터 소스나 Android View 구현 세부사항을 직접 다루지 않는다.
- 도메인 로직과 정책은 UI 클래스가 아니라 UseCase, Mapper, Domain Model 등 적절한 레이어로 옮긴다.
- Repository는 데이터 접근과 데이터 소스 조합을 담당하고, UI 요구사항에 끌려가지 않게 한다.
- DTO, Entity, Domain Model, UI Model의 경계를 흐리지 않는다. 필요한 경우 명시적인 Mapper를 둔다.
- 생명주기를 고려해 Flow/Coroutine을 수집하고, View, Dialog, PopupWindow, Adapter, Coroutine 작업이 누수되지 않게 한다.
- XML 레이아웃은 읽기 쉽고 제약이 명확해야 한다. 특정 기기 크기에서만 우연히 맞는 위치 계산을 피한다.
- 일관성이 좋아지는 경우 dimension, color, string, style 같은 리소스를 적극 활용한다.

## 리팩토링 원칙

- 리팩토링의 우선순위는 관심사 분리와 레이어 경계 회복에 둔다.
- UI 클래스가 비대해져 있으면 UI 표시, 상태 생성, 비즈니스 규칙, 데이터 변환 중 어떤 책임을 분리할 수 있는지 먼저 본다.
- 같은 변경 범위 안에서 레이어 침범이 보이면 동작을 유지한 채 작은 단위로 바로잡는다.
- 한 번에 모든 구조를 고치려 하지 말고, 현재 작업과 맞닿은 경계부터 작고 검증 가능하게 개선한다.
- 로직을 추출하거나 레이어 간 계약을 바꿀 때는 회귀를 막을 수 있는 좁고 명확한 테스트를 추가한다.
